# sts2-cli

<details open>
<summary><b>English</b></summary>

A CLI for Slay the Spire 2.

Runs the real game engine headless in your terminal — all damage, card effects, enemy AI, relics, and RNG are identical to the actual game. Everything is unlocked from the start: all characters, cards, relics, potions, and ascension levels — no timeline progression required.

![demo](docs/demo_en.gif)

## Setup

Requirements:
- [Slay the Spire 2](https://store.steampowered.com/app/2868840/Slay_the_Spire_2/) on Steam
- [.NET 9+ SDK](https://dotnet.microsoft.com/download)
- Python 3.9+

```bash
git clone https://github.com/wuhao21/sts2-cli.git
cd sts2-cli
./setup.sh      # copies DLLs from Steam → IL patches → builds
```

Or just run `python3 python/play.py` — it auto-detects and sets up on first run.

Tested with **v0.111.0 (Steam public-beta, build 24724944)**. After updating the
installed game in Steam, rerun `./setup.sh` to refresh the engine DLLs, patches,
and official English/Chinese localization, then rebuild. Other game versions
may require adapter changes.

For a compatibility check, run `python3 python/play_full_run.py 5 Ironclad`
(repeat for Silent, Defect, Regent, and Necrobinder). A completed run reaches
victory or defeat; crashes, stalls, and timeouts return a nonzero exit code.

## Play

```bash
python3 python/play.py                        # interactive (Chinese)
python3 python/play.py --lang en              # interactive (English)
python3 python/play.py --ascension 10         # Ascension 10
python3 python/play.py --character Silent      # play as Silent
```

Type `help` in-game:

```
  help     — show help
  map      — show map
  deck     — show deck
  potions  — show potions
  relics   — show relics
  quit     — quit

  Map:     enter path number (0, 1, 2)
  Combat:  card index / e (end turn) / p0 (use potion)
  Reward:  card index / s (skip)
  Rest:    option index
  Event:   option index / leave
  Shop:    c0 (card) / r0 (relic) / p0 (potion) / rm (remove) / leave
```

## JSON Protocol

For programmatic control (AI agents, RL, etc.), communicate via stdin/stdout JSON:

```bash
dotnet run --project src/Sts2Headless/Sts2Headless.csproj
```

```json
{"cmd": "start_run", "character": "Ironclad", "seed": "test", "ascension": 0}
{"cmd": "action", "action": "play_card", "args": {"card_index": 0, "target_index": 0}}
{"cmd": "action", "action": "end_turn"}
{"cmd": "action", "action": "select_map_node", "args": {"col": 3, "row": 1}}
{"cmd": "action", "action": "skip_card_reward"}
{"cmd": "quit"}
```

Each command returns a JSON decision point (`map_select` / `combat_play` / `card_reward` / `rest_site` / `event_choice` / `shop` / `game_over`). All names are in English.

### Many runs per process, snapshot / restore

One process can play any number of runs: send `start_run` (or `load_save`) again and the previous run is cleaned up, so a reused process behaves exactly like a fresh one. Starting a run takes about 50 ms instead of about 700 ms for a new process.

For search, any decision point can be snapshotted and restored inside the same process:

```json
{"cmd": "snapshot"}
{"cmd": "restore", "id": 1}
{"cmd": "checksum"}
{"cmd": "drop_snapshots"}
```

- `snapshot` returns `{"type": "snapshot", "id": N, ...}` and costs almost nothing.
- `restore` returns the decision point as it was when the snapshot was taken. It typically takes 3–15 ms, and longer when many commands have to be replayed.
- `{"cmd": "determinize", "seed": N}` (in combat) shuffles the draw pile and reseeds every combat RNG: monster AI, shuffles, targets, card, potion and orb generation, and energy costs. It is for search rollouts that must not peek at the real hidden future. The same seed gives the same future, and it is recorded and replayed like any action, so restoring an earlier snapshot undoes it.
- Each enemy in a combat state has an `index`, its position among living enemies (use it as `target_index`; it shifts when an enemy dies), and an `id`, the game's `CombatId`, which stays fixed for the whole combat.
- `checksum` fingerprints the full combat state (the game's own `NetFullCombatState`) and the run-level save. Use it to check that a restore is exact.

Debug commands for memory work: `gc_stats` (heap after a full GC, working set, snapshot store size), `static_audit` (sizes of collections reachable from game statics) and `heap_census` (reachable instances and sizes by type, with root paths for a `focus` type).

How it works: the engine keeps a checkpoint at run start, at every `load_save`, and before entering each map node. It also logs every state-changing command after the checkpoint. A restore rebuilds the checkpoint and replays the logged commands. This is the same design as the game's own combat replays (`CombatReplay`: a `SerializableRun` plus the recorded actions). It depends on the engine being deterministic, which `tests/test_snapshot_restore.py` and `tests/test_process_reuse.py` check.

## Game Logs

Every run is automatically logged to `logs/` as a JSONL file (one JSON per line), recording each game state and action with timestamps. Logs older than 7 days are cleaned up automatically.

```bash
python3 python/play.py --no-log    # disable logging
```

**When filing a bug report, please attach the relevant log file from `logs/`** — it contains the full step-by-step game state needed to reproduce the issue.

### 同一进程连续开局、快照与恢复

同一个进程可以连续打任意多局：再发一次 `start_run`（或 `load_save`），上一局会被清理干净，复用进程和新开进程的行为完全一致。开局约 50 毫秒，新开进程约 700 毫秒。

给搜索用的快照和恢复都在同一进程内完成：

```json
{"cmd": "snapshot"}
{"cmd": "restore", "id": 1}
{"cmd": "checksum"}
{"cmd": "drop_snapshots"}
```

- `snapshot` 返回 `{"type": "snapshot", "id": N, ...}`，几乎不花时间。
- `restore` 返回拍快照时的那个决策点，通常 3–15 毫秒；需要重放的命令越多，耗时越长。
- `checksum` 给完整战斗状态（游戏自带的 `NetFullCombatState`）和跑图存档做指纹，用来验证恢复是否精确。

原理：引擎在开局、每次 `load_save`、每次进入地图节点之前各存一个检查点，并记录检查点之后每条会改变状态的命令。恢复时先重建检查点，再重放这些命令。这和游戏自带的战斗回放（`CombatReplay`：`SerializableRun` 加录下的动作）是同一种设计，依赖引擎的确定性；`tests/test_snapshot_restore.py` 和 `tests/test_process_reuse.py` 会检查这一点。

## 游戏日志

每局游戏会自动记录到 `logs/` 目录下的 JSONL 文件中，包含每一步的游戏状态和操作，附带时间戳。超过 7 天的旧日志会自动清理。

```bash
python3 python/play.py --no-log    # 关闭日志
```

**提交 bug 报告时，请附上 `logs/` 中对应的日志文件** — 它包含了复现问题所需的完整游戏步骤。
